# Этап 3. Архив сообщений Telegram

## Состояние на 25 ноября 2026 года

Архив уже пополнялся на момент снимка Thai CRM от 24 ноября. В дампе
`botdbthai_2026-11-24_18-55-11.dump` есть 464 сообщения из 13 чатов,
из них 162 входящих и 302 исходящих, и 492 записи о ревизиях, включая исходные
версии. Все сообщения получены через Bot API. Есть одно вложение со статусом
`skipped` и ноль вложений со статусом `ready`. В журналах выгрузок и импортов
ноль записей. Запрос может завершиться до регистрации выгрузки, например если
чат не найден или сотруднику отказано в доступе. Причина, по которой выгрузками
не пользовались, по дампу неизвестна. Текущую конфигурацию сервера предстоит
сверить по инструкции ниже.

Backend с `main.py` и настроенным токеном запускает Telegram polling.
`setup_message_archive` подключает входящие сообщения и правки, сохраняет
сообщения, возвращённые при успешных вызовах Telegram API, и запускает очередь
медиа. `MessageArchiveRepo` хранит сообщения, ревизии и метаданные вложений в
Thai PostgreSQL. В текущей реализации скачиваются фото и голосовые. Бот
ищет чаты по текущим и прежним названиям, а также по имени связанного клиента.
Отдельный запуск `api.thai_server` работает в режиме API-only, без polling.
[Подключение архива](CRM%C2%A0THB/app/setup_handlers.py) ·
[Запуск бота](CRM%C2%A0THB/bot_app.py) ·
[Команда выгрузки](CRM%C2%A0THB/handlers/message_archive.py)

При ошибке создания каталога медиа или экспорта backend запускается без
архива и пишет `Message archive unavailable: could not initialize storage`.
После восстановления доступа к каталогу нужен перезапуск backend. Если при
старте не удалось прочитать очередь отложенных вложений, архив логирует ошибку
и повторяет чтение в фоновом цикле. Эти сценарии и сбой записи сообщения
проверены с рабочей тестовой финансовой БД. [Сквозные тесты](CRM%C2%A0THB/tests/thai/test_auxiliary_commands.py)

## Пилот с тестовым ботом

Локальный пилот прошёл с записью в отдельную PostgreSQL и имитацией Telegram
API. Проверены входящие, исходящие, повтор правки, фото и голосовое, поиск по
имени связанного клиента, ZIP/HTML с медиа, отказ вне админского чата и без прав,
отзыв доступа у уже запрошенной выгрузки и очистка временных файлов. Кассовая
команда и доставка outbox прошли при отказе записи архива. При отключении бот
отвечает на `/сообщение`, что архивирование выключено, и перестаёт сохранять
сообщения. Доставка обновлений живым Telegram-ботом ожидает отдельной проверки.

1. В отдельной копии backend создать `.env.thai` с собственной пустой Thai БД
   на отдельном порту, отдельным JWT-секретом и `CRM_API_ENABLED=false`. Выдать
   токен отдельного тестового бота (`BOT_TOKEN`). Задать Telegram ID тестового
   администратора в `ADMIN_IDS`, тестовый админский чат в `ADMIN_CHAT_ID` и
   `MESSAGE_ARCHIVE_ENABLED=true`. Использовать отдельные каталоги для медиа и
   экспорта. Запустить `.venv/bin/python main.py` из этой копии backend.
2. Добавить бота только в контролируемый исходный и тестовый админский чаты.
   Отправить обычный текст, отредактировать его, отправить фото и голосовое.
   Выполнить `/whoami`, чтобы получить исходящий ответ. Проверить прирост
   входящих и исходящих по сводной диагностике ниже, подставив тестовые порт и
   БД. Дождаться `ready` для обоих вложений.
3. В тестовом админском чате выполнить `/сообщение <название тестового чата>`.
   Открыть ZIP и сверить исправленный текст, исходящий ответ и вложения. Убедиться,
   что у запроса появился статус `completed`, а временный каталог очищен.
   Выполнить ту же команду из исходного чата и от участника без роли в админском
   чате. В обоих случаях ожидается отказ в выдаче файла.
4. Установить в тестовом `.env.thai` `MESSAGE_ARCHIVE_ENABLED=false` и
   перезапустить тестовый процесс. Отправить новое сообщение и `/whoami`,
   проверить ответ бота и отсутствие прироста архива. Для повторного включения
   выставить `true` и перезапустить процесс.

## Проверка на сервере

Сначала проверить текущий режим и каталоги из корневого терминала. Команды
выводят настройки архива и сводные показатели без текстов переписки и секретов.

```bash
cd /opt/skyex-thai/current
systemctl show skyex-thai-backend -p ExecStart -p WorkingDirectory -p ActiveState
runuser -u skyex-thai -- .venv/bin/python - <<'PY'
from pathlib import Path
import os

from config import Config

cfg = Config.load('.env.thai')
print('archive_enabled:', cfg.message_archive_enabled)
print('bot_configured:', bool(cfg.bot_token))
print('admin_chat_configured:', bool(cfg.admin_chat_id))
for name, value in (
    ('media', cfg.message_archive_media_dir),
    ('exports', cfg.message_archive_temp_dir),
):
    path = Path(value).expanduser().resolve()
    print(name, path, 'writable:', path.is_dir() and os.access(path, os.W_OK | os.X_OK))
PY
journalctl -u skyex-thai-backend --since '30 minutes ago' --no-pager \
  --grep 'Message archive health|Message archive unavailable|Failed to (archive|recover pending message archive media)|Run polling'
df -h /opt/skyex-thai/shared/runtime
```

Сравнить следующие счётчики до и после сообщения в согласованном чате.
Монитор пишет сводку при старте и затем примерно раз в пять минут.

```bash
runuser -u postgres -- psql -X -p 5433 -d thai_crm -v ON_ERROR_STOP=1 <<'SQL'
BEGIN READ ONLY;
SELECT direction, count(*), max(sent_at) AS latest_message
FROM message_archive_messages GROUP BY direction ORDER BY direction;
SELECT count(*) AS revisions FROM message_archive_revisions;
SELECT download_status, count(*) FROM message_archive_attachments GROUP BY download_status;
SELECT status, count(*) FROM message_archive_exports GROUP BY status;
COMMIT;
SQL
```

Если архив включён и счётчики растут, можно проверять `/сообщение` в согласованном
админском чате без перезапуска. Если ответ бота сохраняется, а обычное сообщение
из того же чата не появилось, проверить, получает ли бот новые обновления
для этого чата. Нулевое число готовых вложений проверять пилотным фото и
голосовым, сверяя статус загрузки и доступ к каталогу.

## Включение и откат

- Перед включением согласовать охват. При включённом архиве сохраняются сообщения,
  которые бот получает или отправляет во всех доступных ему чатах. `ADMIN_CHAT_ID`
  ограничивает место выгрузки. Если нужен сбор только из выбранных рабочих
  чатов, сначала добавить единый фильтр на запись в обоих направлениях и
  проверить его в пилоте. Согласовать состав админского чата, поскольку ZIP
  отправляется туда. Доступ к команде имеют активные сотрудники с ролями
  `manager`, `accountant`, `owner` или `admin`. При пустом `ADMIN_CHAT_ID` таким
  сотрудникам доступна выгрузка в личном чате с ботом.
- Убедиться, что каталог медиа находится в постоянном хранилище за `.runtime`,
  доступен `skyex-thai`, и на диске есть место для медиа и сборки ZIP. Файлы
  из каталога медиа резервировать отдельно от PostgreSQL, который хранит их
  метаданные. Временные выгрузки проверять отдельно от постоянных вложений.
- Если нужно включить архив, сохранить защищённую копию конфигурации и открыть
  рабочий файл. Указать в нём `MESSAGE_ARCHIVE_ENABLED=true` и согласованный
  `ADMIN_CHAT_ID`. Канонический ключ имеет приоритет над непустым алиасом
  `THAI_MESSAGE_ARCHIVE_ENABLED`. Пустое значение без алиаса даёт `true`.

  ```bash
  (umask 077; cp /opt/skyex-thai/shared/.env.thai "/root/skyex-thai.env.before-archive.$(date +%F-%H%M%S)")
  nano /opt/skyex-thai/shared/.env.thai
  systemctl restart skyex-thai-backend
  systemctl is-active skyex-thai-backend
  curl --fail --retry 8 --retry-connrefused --retry-delay 1 http://127.0.0.1:8001/health/ready
  ```

- После перезапуска сверить polling, счётчики, готовность вложений и выгрузку в
  согласованном админском чате. При откате поставить в том же файле явное
  `MESSAGE_ARCHIVE_ENABLED=false`, перезапустить backend и проверить health и
  ответ `/сообщение`. Уже сохранённые данные и медиа остаются на месте.

## Импорт прежней истории

Импорт Telegram Desktop выполняется по отдельному решению. На изолированной
копии с отдельной БД и каталогом медиа подготовить JSON сопоставления ID
Telegram Desktop с ID тех же чатов в Bot API. Сначала запустить `--dry-run` и
проверить сопоставление, количество сообщений и отсутствие пропущенных файлов.
`--apply` читает `.env.thai` из текущего каталога. Сверить настройки тестовой
БД и каталога перед запуском, держать выгрузку и её вложения вместе.

```bash
.venv/bin/python -m scripts.import_telegram_history \
  --input /path/to/test-export/result.json --mapping /path/to/test-mapping.json --dry-run
.venv/bin/python -m scripts.import_telegram_history \
  --input /path/to/test-export/result.json --mapping /path/to/test-mapping.json --apply
```

На синтетической выгрузке `--dry-run` нашёл один сопоставленный чат, два
сообщения и все файлы. Первый импорт создал две записи с одним готовым
вложением. Повторный пропустил оба сообщения. В базе осталось две записи, две
исходные ревизии и одно готовое вложение, на диске — один файл. Импорт в
рабочую БД ожидает отдельного решения после проверки на копии.
