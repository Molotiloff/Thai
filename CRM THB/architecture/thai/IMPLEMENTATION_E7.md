# Этап 7. Расходы, расчёты и месячные выписки

Реализация от 9 октября 2026. Миграция `thai_0010` применена только
к отдельной базе `thai_crm` на 5433. Российская база и `.env` не менялись.

## Организация кода

- `domain/expenses.py`: раскрытие долей и FIFO погашения.
- `domain/finance/models.py`: общий алгоритм распределения минимальных единиц
  методом наибольших остатков, используемый и процентными распределениями.
- `services/expenses`: сценарии расходов, расчётов, сторно, закрытия и ревизии;
  порты отделяют их от PostgreSQL и HTTP.
- `db_asyncpg/thai_expenses`: репозитории, Unit of Work и запросы.
- `api/thai_expenses.py`: проверка входных DTO и вызов application services.

Все финансовые сценарии используют существующие `OperationPostingService`
и `ReversalService`: журнал, документ, распределения, проекции и outbox
сохраняются одной транзакцией. Готовые операции и выписки не редактируются.
Операции реестра расходов сериализованы одной транзакционной блокировкой;
это исключает переплату и несогласованную выписку при закрытии месяца.

## Расход

Поля: категория, бизнес-дата, инструмент, сумма, ручной курс, комментарий,
плательщик `pe`, `skyex`, `daniyar` или `business`, четыре исходные доли
`pe` / `skyex` / `daniyar` / `common`.
Сумма долей — строго 100%; `common` разворачивается поровну собственникам.
Распределение натуральной суммы сохраняет каждую минимальную единицу.
Историческая оценка USDT распределяется по полученным натуральным суммам,
поэтому у нулевой натуральной доли нет ненулевой стоимости.
При равенстве остатков приоритет определяет стабильный party ID.

Личная оплата не меняет кассу и кошельки. В фирменный расход входят только
доли ПЕ/SkyEX. Внешние долги участников перед плательщиком отражаются
в реестре; собственная доля плательщика не создаёт долг перед собой.
Оплата из общей кассы списывает выбранный инструмент по WAC и создаёт
только требование к Данияру по его доле. Разница WAC и ручной оценки
учитывается отдельным валютным результатом USDT.

| Расход 1000 THB; Данияр 20%, common 80%; курс 35 | Платит ПЕ | Платит касса |
|---|---:|---:|
| Касса | 0 | −1000 THB |
| Данияр должен | ПЕ 200 THB | Кассе 200 THB |
| SkyEX должен ПЕ | 400 THB | 0 |
| Бизнес-расход | 22.85714286 USDT | 22.85714286 USDT |
| Автоматическое списание кошелька Данияра | 0 | 0 |

API возвращает `amount_usdt` всего расхода и отдельный `business_usdt`.
Исторический курс не меняется при обновлении рыночного курса.
Возвратные депозиты остаются отложенными: `deposit=true` отклоняется,
чтобы их ошибочно не включили в расход и взаимные долги.

## Погашение и взаимозачёт

Обязательства сохраняются в валюте расхода. Погашение идёт FIFO по дате
и операции; можно выбрать конкретные obligation IDs. Последняя часть
закрывает весь остаток исторической стоимости, включая округление USDT.

- `direct`: личный расчёт между участниками, без движения общей кассы.
- `cash`: должник внёс деньги общей кассе; либо касса возвращает Данияру
  его личное финансирование бизнес-долей. Требуются инструмент той же
  валюты и ручной курс. Погашение не создаёт повторный бизнес-расход.
- `wallet`: отдельное удержание из кошелька должника в пользу общей кассы.
  Клиент должен принадлежать участнику-должнику либо быть явно привязан
  как `daniyar_balance`. Отрицательный кошелёк разрешён.
- `netting`: закрывает встречные обязательства той же пары участников
  только в одной валюте, с распределениями по обеим сторонам.

Личные долги собственников гасятся `direct`. Если для этого участник берёт
деньги из клиентского кошелька, сначала выполняется обычная выдача из
кошелька, затем прямое погашение; эта выдача не маскируется под расход фирмы.

Личная оплата собственника признаёт `personal_expense_funding`, не капитал
оборотки и не доход. Личная оплата Данияром создаёт
`personal_expense_payable` по бизнес-доле. При прямом возврате собственником
или взаимозачёте эта задолженность снимается с переносом в финансирование
соответствующего собственника; новых расходов, доходов и движения кассы нет.
Это уточняет применение правила memorandum: личные долги собственников
не требуют GL, а уже признанное бизнес-обязательство перед несобственником
нельзя оставлять в GL после фактического погашения.
Мелкое погашение с нулевой оставшейся стоимостью USDT использует memorandum,
натуральный долг при этом закрывается полностью.

Сторно расхода запрещено до отмены связанных погашений. Для кассовых
операций дополнительно действуют ограничения последующих движений WAC.
Коррекция выполняется явным сторно и новым проверенным расходом с
`correction_of`: история и связь замены сохраняются, второй вариант
не проводится автоматически. Повтор одного ключа не создаёт второй документ.

## Закрытие и ревизии

Выписка содержит входящий остаток, новые обязательства, погашения,
взаимозачёты, корректировки/сторно и исходящий остаток по паре и валюте.
Текущие суммы показываются также по каждому участнику: сколько он должен,
сколько должны ему и знаковый `net_payable`. Это представление не выполняет
автоматический взаимозачёт. Капитал, займы и прибыль в выписку не входят.

Менеджер закрывает месяц атомарно; повтор того же ключа возвращает прежний
результат. Другой ключ не закрывает уже закрытый месяц повторно.
Новые расходы и расчёты задним числом в закрытый месяц блокируются.
В следующем месяце остаток вычисляется из прежних обязательств, без
копирования долгов и повторных начислений.

Владелец/администратор может открыть ревизию с причиной. Для каждой
корректирующей операции явно передаётся `revision_id`, соответствующий
месяцу; обычные менеджерские операции в него по-прежнему запрещены.
Завершение ревизии создаёт новый снимок, прежний доступен по номеру ревизии.
После завершения ID не разрешает дальнейшие корректировки.
Если пересмотр раннего месяца изменяет основу более поздних закрытых
выписок, они возвращают `needs_revision=true`; их старые снимки сохраняются,
для актуального входящего остатка требуется отдельная новая ревизия.
Закрытие всего финансового журнала (`ledger`) нельзя обойти ревизией одного
реестра расходов; общий пересмотр результата относится к следующим этапам.

## API

- `GET /api/v1/expense-categories`, `GET /api/v1/expense-participants`.
- `GET/POST /api/v1/expenses`, `GET /api/v1/expenses/{id}`.
- `GET /api/v1/expense-debts` — обязательства, суммы по парам и участникам.
- `POST /api/v1/expense-settlements`, `GET /api/v1/expense-settlements/{id}`.
- `POST /api/v1/expense-operations/{operation_id}/reversal`.
- `GET /api/v1/expense-statements?period=YYYY-MM-01&revision=N`.
- `POST /api/v1/expense-periods/close`.
- `GET/POST /api/v1/expense-periods/revisions`.

Деньги и проценты передаются строками. Время учёта — Asia/Bangkok.
API и сервисы проверяют права независимо. Интерфейс расходов в копии
bookkeeping подключается в E9; backend этапа E7 готов к интеграции.

отрицательный кошелёк только при явном удержании, FIFO между расходами,
обе стороны взаимозачёта, запрет переплаты, коррекция, перенос месяца,
неизменность прежней выписки, права и область ревизии, конкурентные
