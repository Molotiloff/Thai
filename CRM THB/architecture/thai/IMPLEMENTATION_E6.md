# Этап 6. Кошельки, сделки и отдельный Telegram runtime

Реализовано 9 октября 2026. Миграция `thai_0009`: курсы в БД,
сторно сделок, подтверждения сетевых переводов и журнал доставки уведомлений.
Рабочая база — `thai_crm` на 5433. Российская БД на 5432 и `.env` не менялись.

## Проведение и себестоимость

`TradingService` управляет черновиком, готовностью, проведением и отменой.
Telegram и API вызывают одинаковые application services; деньги, документ
сделки, две стороны, снимки курсов, статусы заявки и outbox записываются
одной транзакцией. Общий `MetadataCommandService` обеспечивает аудит
и повторяемость изменений, которые не двигают деньги. SQL находится в
репозиториях, финансовые правила — в сервисах и domain, сборка — в контейнере.

Режим `wallet` меняет обязательства клиента, включая отрицательные остатки,
без кассового движения. Режим `cash` отражает фактический обмен кассы.
Поддержаны любые разные пары из восьми инструментов. При выдаче из кассы
используется WAC, результат учитывается в USDT. Курсы можно указывать
вручную или брать из БД на дату операции; THB — единицы за USDT,
остальные — USDT за единицу. Исторические оценки не переписываются.

Пример: поступление 3600 THB по 35 и выдача 100 USDT с себестоимостью 100
даёт 2.85714286 USDT результата. Касса получает 3600 THB с оценкой
102.85714286 USDT. Обмен в кошельке даёт -3600 THB и +100 USDT клиенту,
касса при этом не меняется. Внесение наличных проводится отдельно.

Перевод THB_CASH↔THB_BANK выделен в `WalletConversionService`.
Сумма перевода и комиссия учитываются отдельно. В режиме `physical`
дополнительно переносится соответствующая себестоимость кассы.
Перевод 3500 THB с комиссией 35 из кошелька 7000 THB по 35 оставляет
3465 THB на исходном счёте, 3500 на втором и 1 USDT комиссионного дохода.

Отмена — точные обратные проводки. Исходный документ остаётся неизменным;
`effective_deals` отображает отмену. Исправление создаёт связанный новый
черновик, который менеджер проверяет и отдельно проводит.
Последующие движения тех же кассовых/клиентских счетов блокируют
небезопасное сторно: сначала отменяются зависимые операции.
Закрытие клиента разрешается только при нулевых кошельках и оценках;
история сохраняется. Регистрация с привязкой чата атомарна.

## Telegram и запуск

`main.py` и `.venv/bin/python main.py` запускают отдельный
Thai runtime. `.venv/bin/python -m api.thai_server` запускает только API.
Настройки читаются исключительно из `.env.thai`; образец — `.env.thai.example`.
Старый `bot_app` не участвует в новой сборке. Google credentials не нужны.

Для живого Telegram запуска необходимы отдельный `THAI_BOT_TOKEN` и
`THAI_ADMIN_IDS` (Telegram user IDs через запятую). При пустой таблице
пользователей runtime создаёт только явно заданных администраторов;
существующие права не изменяются. Без токена работает только API.
`THAI_OPERATIONS_CHAT_ID` — необязательный чат уведомлений;
`THAI_TRONSCAN_API_KEY` включает проверку переводов.
Токены и ключи не наследуются из старой `.env` и не выводятся в repr.
Живой бот и реальные сетевые платежи при разработке не запускались.

Команды `/help`, `/register`, `/bind`, `/balance`, `/statement`, `/deposit`,
`/withdraw`, `/request`, `/ready`, `/post`, `/cancel`, `/correct`, `/undo`,
`/transfer`, `/rates`, `/rate`, `/watch`, `/close`, `/token` используют новую БД.
`/token` доступен только авторизованному сотруднику в личном чате.
Короткие российские команды из архивного runtime здесь не активны.

Финансовое уведомление доставляется после commit через outbox.
Таблица `telegram_deliveries` исключает повторную отправку уже сохранённой
доставки в конкретный чат. Между успешной отправкой Telegram и сохранением
её ID остаётся окно возможного дублирования сообщения при аварии;
финансовая операция при этом не повторяется.

## USDT settlement

Новый мониторинг поддерживает `SINGLE`, выдачу USDT из готовой кассовой
сделки. Проверяются отправитель, получатель, время после старта мониторинга,
точная сумма, USDT, направление OUT и минимум два подтверждения.
Подтверждение и проведение сделки сохраняются атомарно; tx hash уникален.
Обычное проведение сделки с активным мониторингом запрещено.
После таймаута проверка продолжается; таймаут не разрешает обход settlement.
При несовпадении требуется проверка менеджера. API settlement позволяет
уполномоченному сотруднику зарегистрировать подтверждённый факт вручную.
Автоматический монитор получает факты через Tronscan, не использует старые
сервисы финансового проведения. Подтверждённая сетевой выдачей сделка
требует фактического возврата, её нельзя отменить одной записью в журнале.
Старая схема `TEST_THEN_MAIN` не подключается в Thai runtime: тестовый
перевод не считается полным расчётом. Новый `/watch` создаёт только SINGLE.

## Проверки

Проверены кассовый обмен, обмен кошелька до внесения наличных, оба режима
перевода THB и комиссия, точное сторно, коррекция, восемь инструментов,
снимки курсов, Telegram-повторы, конфликт привязки с rollback регистрации,
ограничение токена личным чатом, сохранение доставки, API-цикл заявки и
USDT settlement через тестовый gateway. Google credentials не используются.
Общий результат проверок записан в рабочем чек-листе.
