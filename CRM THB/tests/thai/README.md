# Интеграционные проверки новой цепочки

```sh
.venv/bin/python -m pytest tests/thai tests/design -q
```

Требуются PostgreSQL и THAI_TEST_DATABASE_URL (окружение либо локальный `.env.thai`).
DATABASE_URL существующей CRM не используется. Каждая тестовая база создаётся
с уникальным именем; тесты в `tests/thai` проходят Alembic Thai, а `tests/design`
проверяют отдельно зафиксированный прототип E1. Базы удаляются в finally.

Воспроизводимость seed, повторный upgrade, отказ на чужой базе, независимость
ревизий, отрицательный клиентский остаток при неотрицательной кассе, сохранение
убытка, неизменность документов/курсов/условий и отсутствие CASCADE финансовой
истории проверяются на реальном PostgreSQL. Проверка legacy совместимости
тоже использует отдельную одноразовую базу на этом тестовом сервере.

E10: `test_acceptance.py` проходит вклад собственника и инвестора, два THB-лота,
заём «Партнера», BestChange с отрицательным клиентским кошельком, расход по долям,
ручное начисление процентов, закрытие и выплаты, FIFO и сторно. Далее повреждает
только тестовые проекции, восстанавливает их, делает pg_dump и pg_restore в
другую одноразовую базу и сравнивает все public-таблицы и закрытые отчёты.
Нужны также `pg_dump` и `pg_restore`. Остатки менее 0.000001 USDT не списываются:
журнал хранит 8 знаков, фактическая выплата — 6; остаток остаётся обязательством.
Отдельный тест запускает API-ветку runtime без бота/Google/Tronscan с чужими
legacy-переменными в окружении и проверяет, что используется Thai-конфигурация.
